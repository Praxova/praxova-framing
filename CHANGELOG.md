# Changelog

All notable changes to Praxova Framing are documented here. The project follows [Semantic Versioning](https://semver.org/) with the convention that pre-1.0 versions (0.x) are considered beta — APIs and data model may change between minor versions.

## [0.6.51] — 2026-05-22

Bridge parity for v0.6.50's T joints. The bridge wire format now accepts `joint_type='T_JOINT'` with the new `wall_a_position_in` field; the splice pre-flight composes correctly with T-joint cap notches and backing studs; `frame_building.walls_framed` gains `n_backing_studs` so callers can verify T-joint geometry placement without a follow-up `list_objects` query.

### Added
- **`_JOINT_TYPE_CHOICES` widened** to `("L_CORNER", "T_JOINT")` and **`_JOINT_CORNER_STYLE_CHOICES` widened** to add `"T_BACKING_STUDS"` in `server/handlers.py`. `_parse_joint` accepts `wall_a_position_in` (REQUIRED for T_JOINT, optional/default-0.0 for L_CORNER) and `_joint_to_wire` always emits it. The `add_joint` write loop sets the new PraxovaJoint field. Schema-regularity discipline: parse-return / wire-emit / write-loop field order kept in lockstep.
- **Joint type / corner style combo validation at `add_joint` parse time.** `THREE_STUD` + `T_JOINT` and `T_BACKING_STUDS` + `L_CORNER` both reject with INVALID_PARAMS before any scene mutation, mirroring `templates.validate_joints` error message format. `AUTO` is unconditionally valid for either joint type (resolves later via `templates.resolve_corner_style`). Position bounds (st_a ≤ position ≤ length - wt_b - st_a) are checked at frame_building time via validate_joints — the bridge doesn't read wall_a's length at parse time.
- **`n_backing_studs` field on each `walls_framed` entry** in `frame_building`'s response. Counts Objects whose name starts with `TBacker_Joint` on the wall's children — parallel to `n_corner_fillers` for L corners. Non-zero only when the wall is the through wall (wall_a) in one or more T joints.
- **Seven new smoke-test steps `[35]`-`[41]`** covering the T-joint bridge surface end-to-end. `[35]` add_joint with `joint_type='T_JOINT'` + `wall_a_position_in=80.0` and response echo; `[36]` list_joints_in_level full-field round-trip; `[37]` frame_building with backing-stud + notched-cap geometry (pins `n_backing_studs=2`, `cap.pieces=3`, `cap.splice_xs=[272.0]` — notch boundary at 80/83.5 correctly excluded from splice_xs); `[38]` frame_wall REBUILD on a T-through wall (matches `[37]`'s wall_a `splice_summary`); `[39]`/`[40]` combo-mismatch negatives (`THREE_STUD`+T_JOINT, `T_BACKING_STUDS`+L_CORNER) rejected at add_joint time; `[41]` position-bounds violation succeeds at add_joint but fails at frame_building with a message naming `wall_a_position_in`. Smoke test grows 34 → 41 steps.
- **`_splice_xs_from_pieces` helper in `server/handlers.py`.** Adjacency-aware splice-position extractor: a piece's end-x counts as a splice position only when the next piece starts at the same coordinate (`math.isclose` with `abs_tol=1e-6`). T-joint cap notches don't surface as false-positive splice positions; `n_splices` and `splice_xs` are consistent on multi-range caps.
- **FastMCP `add_joint` "Worked examples" section** showing L_CORNER and T_JOINT call patterns side by side — the highest-leverage docstring addition for LLM callers (matches the smoke `[20]` and `[35]` call patterns verbatim so the example doubles as a sanity reference).

### Changed
- **`_predict_wall_splice_plans` is T-joint aware.** Consumes the v0.6.50 `mid_joints` key on `compute_wall_joint_context`'s return shape. For walls that are wall_a in T joints: derives backing-stud centers via `t_joint_geometry_for_wall_a`, filters OC studs around backing-stud footprints via `filter_studs_around_intervals`, feeds backing studs into `collect_full_height_stud_centers` as eligible splice anchors via the `backing_stud_left_xs` kwarg, and threads `mid_joints` into `plate_effective_ranges` for the CAP plate role only (BOTTOM/LOWER_TOP continue through T positions unmodified per IRC R602.3.2). Per-end joint context loop branches on `ctx['joint_type']` — `l_corner_geometry` is no longer called for T_JOINT ABUTTING ends. Walls with no joints and L-corner-only walls produce byte-for-byte identical splice plans to v0.6.50.
- **`_predict_wall_splice_plans` return shape gains `plate_ranges_count`.** Carries the number of disjoint sub-ranges per plate role (1 for every L-corner-only or no-joint wall; >1 for the CAP of a wall_a in T joints). `_build_splice_summary` consumes this to compute `n_splices` correctly when CAP is multi-piece due to notches rather than stock-fit splices.

## [0.6.50] — 2026-05-19

### Added
- **T joints between walls** (`joint_type='T_JOINT'` on PraxovaJoint, alongside `L_CORNER`). One wall (the abutting wall, `wall_b`) butts into the side of a through wall (`wall_a`) at a position along `wall_a`'s length. Standard residential intersection where an interior partition meets an exterior wall, or two interior partitions cross. Existing L_CORNER joints keep working — purely additive enum widening.
- **`wall_a_position_in: FloatProperty` on PraxovaJoint.** For T joints, the wall_a-local x where wall_b's near edge connects. Ignored for L_CORNER joints. `min=0.0`, `soft_max=1200.0`, `unit='LENGTH'`.
- **`T_BACKING_STUDS` corner style.** Two backing studs on the through wall flanking the abutting wall's end-stud footprint, providing drywall nailing for wall_b's interior face return on both sides. With wall_b's own end stud at the joint, that's three studs at the corner cell — mirrors THREE_STUD's stud count for L corners. `corner_style='AUTO'` resolves to `T_BACKING_STUDS` for T_JOINT joints (unconditional; the Building's `default_corner_style` stays L-only this cycle since `T_BACKING_STUDS` is the only T-joint style).
- **Cap plate notch on the through wall** (per IRC R602.3.2). Wall_a's cap plate is interrupted at the joint position by a `wt_b`-wide gap (= wall_b's wall thickness, e.g. 3.5" for 2x4 wall_b). The wall_a cap becomes multi-piece; each sub-range goes through the v0.6.40 splice planner independently. Bottom and lower top plates continue through the joint without modification — only the cap is notched.
- **Cap plate extension on the abutting wall.** Wall_b's cap plate extends past wall_b's nominal end by `wt_a` (= wall_a's wall thickness) at the joint end, landing in the notch and sitting on top of wall_a's lower top plate. Standard residential T-joint lap.
- **Backing stud placement.** Two full-height `TBacker_Joint<NN>_L` and `TBacker_Joint<NN>_R` objects per T joint, parented to wall_a's Empty. Share `stud_mesh` / `stud_label` / `stud_length_in` / `stud_stock_in` with the wall's regular OC studs (identical cross-section + length, different role at the joint). Mirrors v0.6's `CornerFiller_Joint<NN>` naming convention.
- **OC stud filtering around backing studs.** wall_a's regular OC studs whose footprint would overlap a backing-stud x-range are dropped. Generic interval-overlap filter — same pattern v0.5 uses to drop OC studs around opening king brackets.
- **New pure helper `templates.t_joint_geometry_for_wall_a(position_in, st_a, wt_b)`.** Single source of truth for the through-wall geometry of a T joint: returns `backing_stud_xs` (left-edge x-coords of the two backing studs flanking wall_b's footprint) and `cap_notch_range` (the gap in wall_a's cap). Pure function — takes floats, returns floats.
- **New pure helper `templates.filter_studs_around_intervals(stud_xs, stud_thickness_in, blocking_intervals)`.** Generalization of `filter_studs_around_openings` to raw `(start_x, end_x)` intervals. Used by `frame_wall` for OC-stud filtering around T-joint backing-stud footprints. `filter_studs_around_openings` left untouched for backward compat; could be refactored later as a thin wrapper if the two filters' shapes converge further.
- **N-panel joint detail panel: joint_type-conditional draws.** The detail panel branches on `joint_type` — L_CORNER shows `wall_a_end` / `extending_wall` / the Resolved MAIN readout (existing v0.6.25 behavior); T_JOINT shows `wall_a_position_in` with a carpenter-format readout (`= 8' 0.0"`) below it instead. Common fields (joint_type, wall_a, wall_b, wall_b_end, corner_style) render unconditionally.
- **Joints UIList: T-joint row format.** T-joint rows append `@<pos>"` after the joint type label (e.g. `Wall_01 -> Wall_02   T joint @96"   T_BACKING_STUDS`), so T joints are distinguishable from L corners at a glance without opening the detail panel. GRID layout shows `"T"` for T joints, `"L"` for L corners.
- **`validate_joints` extension: joint_type/corner_style compatibility check.** Rejects `THREE_STUD` with `T_JOINT` ("Joint N: corner_style 'THREE_STUD' is only valid with joint_type 'L_CORNER'") and `T_BACKING_STUDS` with `L_CORNER` (the inverse). `AUTO` always valid (resolves later via `resolve_corner_style`).
- **`validate_joints` extension: T-joint position bounds (loose).** For T_JOINT joints, `wall_a_position_in` must satisfy `st_a ≤ position ≤ wall_a_length - wt_b - st_a` so backing studs and wall_b's footprint fit within wall_a. Error message identifies the offending joint, the actual position, the valid range, and the wall name. Cross-feature overlap checks (T-joint backing studs vs opening kings, vs L-corner end studs, vs other T joints on the same wall) are deferred — downstream collisions surface as bracket/stock-fit errors or visually in the viewport.
- **`collect_full_height_stud_centers` extension: `backing_stud_left_xs` keyword-only param** (default `()`). Backing studs are full-height and provide a continuous load path from bottom plate to cap, so they're eligible splice anchors for wall_a's plates per the v0.6.40 splice algorithm. Composition: T-joint geometry creates new splice anchors that the v0.6.40 splice planner consumes naturally.
- **`n_splices` counter is joint-aware.** Computed as `len(pieces) - len(plate_ranges[role])` per plate role rather than `len(pieces) - 1`. For walls without T-joint cap notches, behavior is byte-for-byte identical to v0.6.41 (all `plate_ranges` lists are single-element). For wall_a with a T joint, a multi-piece cap from the notch (no actual splices in the sub-ranges) correctly reports 0 splices instead of `>=1`.

### Changed
- **`templates.plate_effective_range` → `templates.plate_effective_ranges`.** Returns `list[tuple[float, float]]` instead of a single tuple — one entry per contiguous range of the plate after end mods + interior T-joint notches. Single-element list for plates without notches; multi-element list when wall_a's cap is notched. New keyword-only kwargs: `joint_type_at_start` / `joint_type_at_end` (default `None` → backward-compat L_CORNER semantics for callers that haven't migrated), `mid_joints` (default `None` → no notches; takes a list of `{position_in, paired_wt}` dicts for cap-only notch partitioning). The full per-end behavior table (MAIN/ABUTTING × L_CORNER/T_JOINT × BOTTOM/LOWER_TOP/CAP) is documented in the helper's docstring; the T_JOINT ABUTTING CAP case extends OUTBOARD by `paired_t` (negative `start_x` or `end_x > wall_length_in` is allowed and handled naturally by the operator's placement loop).
- **`templates.compute_wall_joint_context` return shape.** Gains `'mid_joints'` key (always present, list of T-joint contexts where this wall is wall_a). Empty list for L-corner-only walls and walls without joints. Each mid_joint entry carries `joint_type`, `joint_index` (1-based, for naming), `position_in`, `paired_wall`, `paired_wall_end`, `corner_style` (resolved). Per-end entries (`'START'` / `'END'`) gain a T_JOINT ABUTTING path (when this wall is wall_b in a T joint, the context goes in START or END based on `wall_b_end`, with `role='ABUTTING'` hardcoded — T joints have a fixed through/abutting topology, no extending_wall resolution).
- **`templates.resolve_corner_style` is joint-type-aware.** For `corner_style='AUTO'`, branches on `joint_type`: L_CORNER → `building_default` (existing behavior, still `'THREE_STUD'` in v0.6.x); T_JOINT → `'T_BACKING_STUDS'` (unconditional). Explicit values honored verbatim — `validate_joints` rejects mismatches up front so this function doesn't have to defend against them.
- **`templates.validate_joints` duplicate-(wall, end) check is joint_type-aware.** T_JOINT joints don't bind wall_a's end (the joint is at a position along the wall, not at an end). The duplicate-check loop only adds `(wall_a, wall_a_end)` for L_CORNER joints; `(wall_b, wall_b_end)` is checked for both joint types. Catches "L_CORNER's wall_b_end collides with another joint's wall_b_end", "L_CORNER vs T_JOINT wall_b_end collision", etc.
- **`ops_frame._resolve_joint_context` populates `mid_joints` for `plate_effective_ranges`.** Translates `joint_context['mid_joints']` into the `{position_in, paired_wt}` dicts the helper consumes; `paired_wt` is `LUMBER_TYPES[paired_nominal][1]` (wall thickness, the `wt_B` not `st_B` per the v0.6.50 design — wall_b is rotated 90° relative to wall_a so wall_b's local-Y maps to wall_a's local-X).
- **`ops_frame.frame_wall.execute()` plate placement loops iterate the new list shape.** For each `plate_role`, outer `for r_start, r_end in plate_ranges[role]` wraps the existing per-piece splice iteration. For walls without notches, runs once per role with identical behavior to v0.6.41.
- **`server/handlers.py:_predict_wall_splice_plans`** updated for the new shape with the same iterate-and-extend pattern. Passes `mid_joints=None` (T-joint awareness on the bridge lands in v0.6.51 — the bridge wire format doesn't yet accept `joint_type='T_JOINT'`, so bridge-driven framing never has T-joint context to feed in).
- **`ops_frame.py` module docstring refreshed.** Dropped the stale "Joint management ... lands in commit 5" paragraph from v0.6's early draft (those shipped in v0.6 + v0.6.2). "Not in v0.6 (deferred)" list updated: T joints removed (now shipping), in-line splice clarified (the joint_type version that joins two walls end-to-end; distinct from v0.6.40's plate-splice-along-a-wall feature), California / ladder-blocking demoted to "later sprint".
- **`blender_manifest.toml` version** 0.6.41 → 0.6.50.
- **`__init__.py` `__version__`** "0.6.41" → "0.6.50".
- **`smoke_test.py` `addon_version` pin assertion** "0.6.41" → "0.6.50". Method count stays 18 — v0.6.50 is UI-only; the bridge wire format doesn't yet accept `joint_type='T_JOINT'`, so no new smoke steps this cycle. T-joint scenarios land in v0.6.51 alongside the wire format extension.

### Architecture notes
- **T-joint geometry composes with v0.6.40 splice infrastructure cleanly.** Wall_a's cap notch (`wt_b` wide at the joint position) makes the cap multi-piece via `plate_effective_ranges`. The v0.6.40 splice planner already handles per-piece stock-fit splicing, so each cap sub-range becomes an independent splice planning problem. The two concerns are orthogonal — notch positions are joint-geometry-driven, splice positions are stock-length-driven — and stack naturally without the planner needing to know T joints exist. Same applies to backing studs: full-height, eligible splice anchors, fed through the existing `collect_full_height_stud_centers` extension.
- **Wall_b's cap extension is auto-handled by `plate_effective_ranges`.** The helper returns a range that extends past wall_b's nominal footprint by `wt_a` at a T_JOINT ABUTTING end. The operator's existing placement loop computes `piece_length_in = end_x - start_x` and places at `start_x * INCH` — both work with negative `start_x` (joint at START) or `end_x > wall_length_in` (joint at END). No special-case operator code needed for wall_b's cap; just the same iterate-the-list pattern that handles wall_a's notched cap.
- **`wt_B` vs `st_B` distinction.** Wall_b's footprint on wall_a's length axis is wall_b's WALL thickness (`LUMBER_TYPES[paired_nominal][1]`, 3.5" for 2x4), NOT stud thickness (`[0]`, 1.5" for 2x4), because wall_b is rotated 90° relative to wall_a so wall_b's local-Y maps to wall_a's local-X. Backing studs land at `[position - st_a, position]` and `[position + wt_b, position + wt_b + st_a]`. Position validation bounds `st_a ≤ position ≤ wall_a_length - wt_b - st_a`. Same `wt` vs `st` rule of thumb the v0.6 design doc spelled out for L joints: "if it represents how far the OTHER wall takes up space at the corner, use wall thickness [1]; if it's this stud's own width along the wall length, use stud thickness [0]".
- **T joints don't have MAIN/ABUTTING resolution.** wall_a is the through wall by construction; wall_b is the abutting wall by construction; `extending_wall` is not used. `corner_style` with T_JOINT is `T_BACKING_STUDS` (only style available in v0.6.50). `resolve_corner_style` for AUTO branches on `joint_type` to pick the right default — `T_BACKING_STUDS` for T_JOINT, `building_default` for L_CORNER. The Building's `default_corner_style` stays L-only this cycle (no `default_t_style` sibling field); when a future cycle adds more T-joint styles, that's where the sibling lands.
- **Single source of truth for stud-overlap filtering.** `filter_studs_around_intervals` generalizes `filter_studs_around_openings` to raw `(start, end)` intervals. `filter_studs_around_openings` left unchanged for backward compat — could be refactored later as a thin wrapper if the two filters' shapes converge further. Backing studs feed into the same filter via simple interval list construction (`[(b['x'], b['x'] + thickness_in) for b in backing_studs]`); the order — filter around openings, then filter around backing studs — is idempotent (intersection-free filters compose), chosen for diff readability.
- **No smoke-test scenarios added this cycle.** v0.6.50 is a UI-only cycle. The bridge wire format doesn't yet accept `joint_type='T_JOINT'` — that's v0.6.51's work — so the bridge-driven smoke test can't reach T-joint behavior in this cycle. Bumping the `addon_version` pin is the smoke test's only change. Same pattern as v0.6.0 (UI cycle) → v0.6.1 / v0.6.2 (bridge cycles that added the scenarios). T-joint smoke steps will land in v0.6.51 alongside the bridge wire format extension.
- **The five v0.6.50 commits.** (1) `properties.py`: PraxovaJoint enum widening (`T_JOINT` joint_type + `T_BACKING_STUDS` corner_style) + new `wall_a_position_in: FloatProperty` + docstring refresh. (2) `templates.py` + minimal call-site updates in `ops_frame.py` and `server/handlers.py`: `plate_effective_range` → `plate_effective_ranges` refactor + `compute_wall_joint_context` shape extension + `resolve_corner_style` joint-type-aware + new `t_joint_geometry_for_wall_a` helper + `validate_joints` T-joint rules + `collect_full_height_stud_centers` `backing_stud_left_xs` kwarg. (3) `ops_frame.py`: backing-stud derivation + OC filter (new `filter_studs_around_intervals` helper added here for tight coupling with its consumer) + eligible-anchor extension + backing-stud placement loop + `mid_joints` wiring through `plate_effective_ranges` + `n_splices` counter fix + module docstring update. (4) `ui.py`: joint detail panel joint_type-conditional draws (hide `wall_a_end` / `extending_wall` / Resolved MAIN for T_JOINT; show `wall_a_position_in` with carpenter-format readout) + UIList row T-joint format with `@<pos>"`. (5) this release commit — manifest + `__version__` + `smoke_test` pin + CHANGELOG + README.

## [0.6.41] — 2026-05-18

### Added
- **`splice_summary` field on `frame_wall` response.** Replaces the v0.4.1 `plate_stock_in` field, which is no longer meaningful for spliced walls (each piece has its own stock). Shape: `{n_splices: int, bottom: {pieces, splice_xs}, lower_top: {pieces, splice_xs}, cap: {pieces, splice_xs}}`. The `splice_xs` lists give the per-plate butt-joint x-coordinates in wall-local coordinates — so a caller can verify the IRC R602.3.2 24" cap-vs-lower-top offset held without re-running the planner. `n_splices` aggregates across stack-level instances: `bottom_splices * bottom_plate_count + lower_top_splices * (top_plate_count - 1) + cap_splices`.
- **`splice_summary` field on each `frame_building` walls_framed entry.** Same shape as frame_wall's splice_summary — populated from the per-wall pre-flight (see below). Status line confirms the source and exact width when a compatible active object is selected; shows a "Select a sheet or panel" hint otherwise.
- **`templates.fill_axis_width_in(obj)`** — cross-category helper returning the local-Y width in inches for a sheet or panel. Single source of truth used by both the Fill operator and the `fill_span_in` update callback. Returns 0.0 for LUMBER and for unknown size keys, letting callers decide how to handle.
- **`PraxovaSceneProps.fill_count`, `fill_span_in`, `fill_direction`** — three new scene fields backing the UI. The `fill_span_in` update callback (`_on_fill_span_change`) recomputes `fill_count = ceil(span / width)` from the active object's width using the helper above, so clicking a preset atomically sets both span and count.
- **`PRAXOVA_OT_set_fill_span`** internal operator powering the preset buttons (mirrors `PRAXOVA_OT_set_spacing`'s role for the OC duplicator).

### Architecture notes
- Operator mirrors `praxova.duplicate_oc`'s pattern: world-space step from `obj.matrix_world.to_3x3().col[1]` so rotated sources (e.g. roof panels tilted onto a slope) fill along their own width direction rather than along world-Y. Linked-mesh copies via `obj.copy()` — same memory and cut-list semantics as OC Duplicate.
- LUMBER refusal is enforced at three layers: `fill_axis_width_in` returns 0.0 for LUMBER, the operator refuses with a redirect to OC Duplicate, and the UI's "Select a sheet or panel" hint front-loads the obvious case. The hint doesn't disable inputs — users can pre-stage values before selecting a source, mirroring how OC Duplicate behaves.
- Bridge MCP tool intentionally deferred to v0.3.4. v0.3.2 established the "UI parity in vN, bridge parity in vN+1" cycle; v0.3.3 sticks to that.
- The new `templates.fill_axis_width_in` lives in its own "Tag helpers (cross-category)" section between the panel data and mesh construction. Future tag-reading helpers (e.g. for a future export pipeline) have an obvious home there.
- `mcp_server` package version unchanged at 0.3.2 (no MCP-side changes this cycle).

## [0.3.0] — 2026-05-10

### Added
- **MCP bridge.** A localhost JSON-RPC bridge inside Blender (`server/`) and a separate FastMCP server process (`mcp_server/`) so an LLM client like Claude Desktop can drive the existing operators. Eight tools exposed: `add_lumber`, `add_sheet`, `duplicate_oc`, `generate_cutlist`, `set_imperial_units`, `list_materials`, `list_objects`, `get_scene_info`.
- **Bridge operators.** `praxova.start_bridge` and `praxova.stop_bridge` to control the listener.
- **N-panel "MCP Bridge" subsection** with port input, running-state indicator, and start/stop button.
- **Scene property** `bridge_port` (default 9876) for the user to configure the bridge listen port.
- `smoke_test.py` at the repo root: a stdlib-only client that exercises the bridge end-to-end without the MCP layer. Useful for diagnosing protocol issues independently of any MCP client.
- `mcp_server/` Python package (`praxova-framing-mcp` console script) with its own README covering install via `uv tool install` or `pipx install` and Claude Desktop configuration.

### Architecture notes
- The bridge runs a background listener thread inside Blender; each client connection spawns its own thread, but all bpy mutation is dispatched through `bpy.app.timers.register` onto Blender's main thread so concurrent connections cannot race on bpy state.
- The MCP server process opens one short-lived TCP connection per tool call: stateless and robust to bridge restarts. Latency over loopback is sub-millisecond.
- Wire protocol: newline-delimited JSON-RPC 2.0. Error codes follow the standard (-32700, -32600, -32601, -32602, -32603) with app-defined codes in the -32000..-32099 range for empty cut list, missing active object, missing target object, and operator-cancelled outcomes.
- Bridge running-state is module-level transient process state, intentionally NOT a Scene PropertyGroup field — saving and reopening a .blend cannot lie about whether the bridge is up.

### Changed
- `unregister()` now stops the bridge before tearing down the module, so the listener thread doesn't keep a stale module reference after a Blender Reload Scripts.
